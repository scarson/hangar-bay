## Bugs

### Item-bearing segment numerals advertise a population their click cannot deliver while an item-less segment is active

**Location:** `app/frontend/web/src/features/contracts/components/SegmentTabs.tsx:118-123` (numeral), `:77-82` (`segmentPatch` restore), with the count semantics at `app/backend/src/fastapi_app/services/contract_service.py:467-469` and `:504-511`
**Severity:** significant

**Evidence:** While a courier/loan/unknown segment is active, Criterion 1.7 has cleared `ships_only`, so `toApiQuery` sends no `is_ship_contract` (`filters.ts:309`) and `_segment_counts_and_total` computes **every** segment count with `filters.is_ship_contract=None` — i.e. the item-bearing counts in that envelope are the *unfiltered* populations. `SegmentTabs` renders them as-is on the Item exchange and Auction buttons (`counts[segment.type] ?? 0`, line 123). But clicking either button from an item-less segment runs `segmentPatch(type, leavingItemLess=true, …)`, which sets `ships_only: undefined` — restoring the ships-only default per Criterion 1.9 — so the delivered view is the ships-only population. At production magnitudes (spec §1: ~33,900 live contracts, ~411 ship-flagged) the Item exchange button reads ~30,000+ while standing on Courier and delivers ~400 on click, at which point the numeral visibly collapses.

This is exactly the defect class Criterion 1.8 names ("the silent-filter-no-op defect wearing a numeral") and exactly the reasoning codex's PR-C P1 established and D11 fixed **for the All control only**: "the envelope's item-bearing counts were computed without ships-only, and All's destination restores it — a population those numbers cannot describe. No numeral beats a wrong one." The typed item-bearing buttons have the identical exposure and were not covered by the fix. The in-code justification (`SegmentTabs.tsx:113-117`: "the number a segment shows is the number selecting it delivers") is false in precisely this state, and the test suite pins only the All control's hidden numeral (`pages.test.tsx:779-790`); no test examines the typed-segment numerals while an item-less segment is active — the fixture serves static `SEGMENT_COUNTS` either way, so nothing could notice.

**Second manifestation, same root:** the numeral math mixes captured counts with live-URL flags. `ContractsPage` passes the **response's** `segment_counts` but the **live** `search` (`ContractsPage.tsx:247`), and `leavingItemLess` / `allCountsEveryType` are derived from the live search (`SegmentTabs.tsx:95-100`). During the courier→All transition, the live search flips `leavingItemLess` to false immediately, so the All button un-hides its numeral and computes it from the *previous* (courier, lifted) envelope — showing the wrong sum D11 exists to suppress, for the full multi-second duration of the request under `keepPreviousData`. This is the WEB-1 shape (values describing data must travel with the data); the flags interpreting `counts` should come from the same response the counts came from.

**Impact:** A user browsing the courier tab sees "Item exchange 33,844" and gets 411 rows on click — a numeral that lies by two orders of magnitude, in the exact interaction path (leaving an item-less segment) the feature ships as a first-class flow. D11's follow-up note already names the server-side fix (serve Criterion 1.8's mirror — ships-respecting item-bearing counts — on item-less-segment requests); alternatively hide the typed numerals under the same rule as All, and derive the interpretation flags from the response rather than the live URL.

### A spec-conformant contract without `price` poisons the entire aggregation run

**Location:** `app/backend/src/fastapi_app/models/contracts.py:60` (`price: Mapped[float] = mapped_column(Numeric, nullable=False)`) vs `app/backend/src/fastapi_app/services/background_aggregation.py:261` (`"price": c.get("price")`)
**Severity:** significant (latent — has not fired; fires on data ESI is contractually allowed to send)

**Evidence:** The committed ESI spec snapshot (`app/backend/tools/esi_spec_monitor/snapshot.json`, `GET /contracts/public/{region_id}`, both the pinned and newest views) marks `[].price` as `required: false` — the repo's own authority for field optionality (ESI-4: "the machine-readable `properties`, `required` … have been accurate every time we have checked"). `_build_contract_rows` maps it with a bare `.get()`, producing `None` when absent, into a `nullable=False` column. Every other spec-optional field in that mapping is defended: `collateral` and `for_corporation` get defaults, `title`/`reward`/`volume`/`buyout`/`days_to_complete`/both location ids sit over nullable columns. `price` is the one hole.

This is FASTAPI-3's three-link chain (upstream `required` → model `nullable=` → response `Optional`) broken at the upstream→model link — the same audit that fixed `start_location_id` at the *response* link stopped one link short. And the blast radius is worse than FASTAPI-3's one-500-page: the NULL reaches `bulk_upsert` inside `_process_contracts`' single run-wide transaction (`background_aggregation.py:548-554`), so a NOT NULL violation on one row aborts the batch statement, the exception propagates out of `_process_contracts`, the whole transaction rolls back (`run_aggregation`, `:465-484`), and the run records failure. It then **recurs on every subsequent run** for as long as that contract stays in ESI's public list — one price-less contract is a total, self-renewing ingestion outage, not a bad row.

**Impact:** Zero new data corpus-wide (staleness climbing, watermarks frozen, watchlist alerts dead) from a single upstream payload the spec explicitly permits, with the failure surfacing only as a generic aggregation error log. Pre-existing (the mapping predates F008), but F008 is the pre-release audit of exactly this mapping function, and the fix is one decision: either default absent price (couriers already conventionally carry 0) or make the column nullable and the response field stays `Optional` as it already is.

### `formatComposition` naive pluralization corrupts plural-named category names

**Location:** `app/frontend/web/src/features/contracts/format.ts:167`
**Severity:** minor

**Evidence:** `` `${category.item_row_count} ${category.name}${category.item_row_count === 1 ? '' : 's'}` `` appends `s` to the server-supplied dogma category name. Real dogma categories include plural and irregular names: **Accessories** (category 5), **SKINs** (91), **Entity** (11). A mixed lot with two accessory rows renders "2 Accessoriess"; two SKIN rows render "2 SKINss"; two entity rows render "2 Entitys". These are real categories reachable in public contracts (Accessories covers cerebral accelerators and boosters common in contract lots).

**Impact:** Visible garbled text in the composition line — the row summary Criterion 6.1 makes the point of the feature. Cosmetic, but it is a specific wrong string in shipped UI. Cheap fix: pluralize only names that don't already end in `s`, or drop pluralization and render "Accessories ×2"-style counts.

## Design Concerns

- **`search` + `type_ids` compose per joined row, not per contract.** Both are applied as predicates on the same outer-joined item row (`contract_service.py:268-276`, `:341-342`), so a contract holding one item matching the search text and a *different* item matching `type_ids` is excluded — per-row conjunction across two filters, the SQLA-3 shape one level up. Also, both (and the `ship_name` sort aggregate) read **all** items including requested (`is_included=false`) ones, unlike every F008 family, which is offered-only per §3.1. Not flagged as a bug because spec §3.1 explicitly scopes the existential/offered-only rule to the five new columns and these are pre-F008 behaviors — but the codebase now holds two deliberate philosophies side by side in one function, and the next filter added will copy one of them at random.

- **`issuer_id` / `issuer_corporation_id` are `Integer` (int32) columns under a spec-typed int64 field.** `models/contracts.py:70-71` vs snapshot `"[].issuer_id": {"format": "int64"}`. Every other ESI id in the model (`contract_id`, `start_location_id`, `end_location_id`, `item_id`, `record_id`) is `BigInteger`; the issuer pair was left behind. If CCP allocates character/corporation ids above 2^31 — a range expansion they have announced historically — this fails exactly like Bug 2: one contract poisons every run. Worth folding into the same fix.

- **Multi-category + group taxonomy selections silently ignore the group-less categories.** The backend deliberately compiles category+group as one same-item EXISTS (`contract_service.py:365-385`), justified by "the only pairing the cascading rail can send" — but the rail supports multi-select, so a user can hold categories {Ship, Module} with a group under Ship selected; the Module checkbox then contributes nothing (a contract offering only modules cannot match `category IN (Ship,Module) AND group IN (frigate)` on one item). `TaxonomyFilter.tsx` prunes out-of-scope groups on narrowing (`:78-98`) but cannot prevent this state. The spec doesn't define multi-select semantics, so this is a decision to make explicit rather than a defect — but the in-code claim that the state is unreachable is false.

- **Numeral provenance in `SegmentTabs` is structurally mixed** (live-URL flags interpreting captured counts) — the root cause behind Bug 1's transient manifestation. Even after Bug 1 is fixed, any future flag read live beside `data.segment_counts` re-opens a WEB-1 window. Passing the captured request-shape (the response already carries `segment`, `itemFilteredItemLessSegment`, etc. from `useContracts`) into `SegmentTabs` for count interpretation — while keeping live state for `aria-pressed`/selection — closes the class.

- **Testing follow-ups suggested by these findings** (not applied — analysis-only session; candidates for `docs/pitfalls/testing-pitfalls.md` if the fixes land): (1) the segment-count suite pins the All control's hidden numeral in the item-less-active state but never examines the typed item-bearing numerals in that state — the state where their meaning changes; when a control's rendering rule branches on view state, each branch's *other* controls need assertions too. (2) TEST-18's writer-reconciliation discipline has a spec-side sibling: no test ingests a spec-minimal payload (required fields only) through `_build_contract_rows` → `bulk_upsert`; fixtures always hand-write `price`, so the NOT-NULL-over-optional trap is invisible to the whole suite.
