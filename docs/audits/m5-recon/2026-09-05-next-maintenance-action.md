## Ingestion metrics — preferred planning follow-up

**Not shipped.** [The metrics module](../../../app/backend/src/fastapi_app/core/metrics.py) declares the last-success gauge and skipped-contracts counter, with no run-duration, ESI-round-trip or items-fetched instrument. Its latest path commit is `620a87ab6b4e023afe159a30a402c6a2f057974c`: malformed-date handling added the skipped-contract counter. The older audit's claim that this module contains exactly one instrument is stale; the three requested measurements are still absent. [Aggregation](../../../app/backend/src/fastapi_app/services/background_aggregation.py) has `run_aggregation` at line 530 and `_record_run_outcome` at line 612; its freshness record still contains timestamps/outcome/region counts, not those measurements.

**Design choices the dedicated plan must settle:** which interval duration measures (active work versus lock wait, and treatment of skipped/failed runs); whether an ESI count means HTTP attempts, logical calls or successful responses; whether item count means raw page rows, complete fetch results or persisted rows; and metric types, names and bounded labels. These meanings change the evidence used to judge future optimizations and cannot remain implicit. The client is shared by ingestion and request-scoped consumers, so an unconditional global HTTP counter is not automatically an ingestion-only counter. Its GET retry transport and separate POST call sites also need deliberate coverage; see [ESIClient](../../../app/backend/src/fastapi_app/core/esi_client_class.py), lines 368–419 and 482–517, and [request-scoped construction](../../../app/backend/src/fastapi_app/core/dependencies.py), line 51.

**Likely scope and verification:** additive aggregate instruments in `core/metrics.py`, observation sites in aggregation and possibly the ESI-client boundary, focused ingestion/client tests, and an exposition assertion through the existing `/metrics` route. Use exact deltas for success, partial failure, total failure, retry exhaustion, empty results and lock-skipped runs; verify no double counting, no unbounded path/contract labels, and unchanged ingestion outputs. Preserve the bearer gate already tested in [main-endpoint tests](../../../app/backend/src/fastapi_app/tests/api/test_main_endpoints.py), lines 55–72. A local controlled transport plus the dedicated PostgreSQL test database can verify the behavior; production access or Grafana alert creation is not a prerequisite. This is a likely Routine scope only while metrics remain observational and do not change persistence, freshness semantics, API contracts or authorization.

**Independence:** it does not require saved-search or name-sort changes. It overlaps the planned item-fetch implementation's ESI-client/aggregation source and tests. The implementation executor will open that production PR after the two plan tasks; it had not been created when this report was written. Do not develop conflicting edits or auto-merge a dependent Routine PR while that Review-class production PR remains open. Plan against the integrated item-fetch implementation after its production merge; [the git strategy's auto-merge requirements](../../git-strategy.md#auto-merge-the-default) explicitly include overlapping-file conflicts as a dependency on an open Review PR.

## QueueHandler/QueueListener logging — not ready

**Not shipped.** [Logging configuration](../../../app/backend/src/fastapi_app/core/logging.py), lines 58–105, renders structured JSON in the calling processor chain and attaches ordinary stdout/file handlers. No QueueHandler or QueueListener implementation exists under `app/backend/src`. Its latest path commit, `202201ff2c7c59724c4a8a08ea0aa011b7ec6fa8`, closes replaced handlers during reconfiguration; it does not add queueing. [Application lifespan](../../../app/backend/src/fastapi_app/main.py), lines 41–73, configures logging but has no listener lifecycle.

**Design choices the dedicated plan must settle:** queue capacity and overflow policy (drop, block, or memory growth); listener startup, drain, shutdown and reconfiguration ownership; and whether JSON rendering remains in the caller or moves to the consumer. Merely replacing the sink handlers leaves the current JSONRenderer processor on the caller's path, so it cannot substantiate the draft's stronger claim that the event loop “only enqueues.” Moving rendering also requires preserving request context and exception data before crossing threads. These decisions are not specified in the current draft.

**Likely scope and verification:** `core/logging.py`, application lifespan cleanup if a listener is owned there, and [logging tests](../../../app/backend/src/fastapi_app/tests/core/test_logging.py). Preserve the full structured log schema, request IDs and exception content; pin overflow behavior, deterministic drain, final shutdown records, repeated setup, and absence of leaked listener threads/file descriptors. Compare output using fixed event/time inputs and demonstrate event-loop behavior with controlled blocked sinks rather than guessed elapsed-time thresholds. The existing fixture restores process-global logging state, and [HTTP observability tests](../../../app/backend/src/fastapi_app/tests/api/test_observability.py) depend on that restoration. A reviewed design is necessary before promising either lossless logs or nonblocking producers.

**Independence:** source files can be disjoint from item-fetch, saved-search and name-sort changes, but logging is process-global and affects their log assertions. It could become Routine if the final change preserves schema and safety behavior and introduces no architecture trigger; that classification cannot be certified from the current sketch. No implementation was selected from this candidate.
