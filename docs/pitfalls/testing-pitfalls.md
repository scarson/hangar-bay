# Testing Pitfalls

Test scenario checklist for reviewing coverage of any feature. Every item on this list exists because it catches bugs that have occurred in real codebases. Items marked with **🔥 Found in this project** were discovered here specifically. Unmarked items are universal — bugs we haven't made *yet* in this project, but that have bitten other projects hard enough to be worth testing against. Do not deprioritize an unmarked item because it lacks a marker.

> **Relationship to implementation-pitfalls.md:** `implementation-pitfalls.md` specifies *what* to implement and *why*. This document specifies *how to verify* those implementations work correctly. Cross-references between the two are noted inline.

---

## How to Use This Document

**If you're writing tests:** Go to the relevant topic sections below, read the checklist items, and verify your test suite covers each one that applies. Unchecked items are gaps — either add a test or explicitly note why the item doesn't apply to this feature.

**If you're reviewing tests:** Use the checklist to audit coverage gaps. A passing test suite with missing coverage is worse than a failing test suite with complete coverage — you don't know what's actually protected.

**If you're maintaining this document:** When a real bug slips through to production or staging because of a missing test, add the check item to the appropriate section with the 🔥 marker and a one-line note about the observed failure mode. See §How to Add a Testing-Pitfall at the end.

---

## 1. Test Output Pristine

Test output MUST be clean for the suite to pass — no stray errors, warnings, or stack traces. If a test legitimately produces errors (e.g. it's verifying error handling), capture them explicitly and assert on their content. Silent error spam in test output hides real failures.

- [ ] **No unexpected stderr in passing tests.** Any stderr output from a passing test must be explicitly asserted on, or the test is lying about what it verifies.
- [ ] **No unhandled promise rejections / uncaught exceptions.** These often appear as warnings rather than test failures; configure your runner to fail on them.
- [ ] **Deprecation warnings fail the suite or are explicitly tracked.** Silently-warned deprecations become hard breaks on the next runtime upgrade.
- [ ] **Test output doesn't contain debug prints.** Debug statements that escaped into production tests are sometimes the only evidence of a half-finished implementation.

---

## 2. Skipped Tests Are Not Passing Tests

A test that's `skip`ped, `xit`'d, `pending`, or `@Ignore`d is a test that's not running. A CI job that says "100 tests passed, 5 skipped" is NOT the same as "105 tests passed."

- [ ] **No unexplained skips in the suite.** Every skipped test has a comment explaining why it's skipped and under what condition it should be re-enabled.
- [ ] **Skips with a linked issue/ticket.** A skip without follow-up context is forgotten work.
- [ ] **CI distinguishes skipped from passed in its summary.** If the report doesn't separate them, skipped failures hide.
- [ ] **Skip counts are tracked over time.** Growing skip count = eroding coverage.
- [ ] **No assertion block is guarded by a condition on the thing it asserts.** `if results: assert ...` skips itself precisely when the code breaks, and no skip count reports it. See TEST-20 in §8.

---

## 3. Error Path Coverage

Silent error swallowing is one of the largest bug categories in any codebase. Every error path must be tested explicitly — not just "the happy path works."

- [ ] **Each error branch has a test that triggers it.** If a function has 5 ways to return an error, there are 5 tests covering each one.
- [ ] **Error messages are asserted, not just error presence.** `expect(err).toBeTruthy()` doesn't catch "wrong error returned"; `expect(err.message).toMatch(/expected pattern/)` does.
- [ ] **Information leakage via error codes checked.** When a handler must return the same status code regardless of whether a resource exists (anti-enumeration), test that ALL error paths return the same status — including DB errors on post-lookup queries that leak existence.
- [ ] **Error-path side effects verified.** If an error path is supposed to roll back state / release a lock / clear a cache, assert that it did.
- [ ] **Error-path resource cleanup verified.** Acquired resources (file handles, DB connections, semaphores) must be released even on error. Test with `defer`-equivalent patterns or explicit cleanup assertions.
- [ ] **The injected failure is of the class production actually raises.** A convenience `RuntimeError` carries none of the payload a real driver/library exception carries, so any assertion about the rendered error holds for the wrong reason. See TEST-21 in §8.

## 4. Negative Property Testing

Happy-path tests prove "it works" for one input. Negative property tests prove "it doesn't break" under stress, boundaries, and adversarial input. The latter catches the bugs that ship.

- [ ] **Cleanup and eviction.** When code accumulates state (maps, caches, queues), test that stale entries are eventually cleaned up. Don't just test "it works" — test "it doesn't leak."
- [ ] **Bounded growth.** For any in-memory data structure that grows with external input, test that it has a maximum size or eviction policy. Simulate 1000+ entries and verify memory is bounded.
- [ ] **Case sensitivity where identity matters.** When a string key is used for identity (email, username, path), test that case variations are treated consistently. `Admin@Example.com` and `admin@example.com` must be the same identity — or consistently different ones.
- [ ] **Empty / null / zero inputs.** Every parameter that accepts a value should be tested with empty string, null, zero, empty array, empty map. "Did not crash" is not the same as "handled correctly."
- [ ] **Oversized inputs.** Long strings, deeply nested structures, large collections. Where are your truncation / rejection boundaries, and are they enforced?
- [ ] **Unicode / encoding edge cases.** Multi-byte chars, combining sequences, RTL text, emoji, zero-width joiners, NUL bytes. Anywhere strings cross a boundary (storage, display, comparison) needs this.

## 5. Concurrency & TOCTOU

If the code can be executed concurrently, test it concurrently. Single-threaded happy-path tests don't catch race conditions.

- [ ] **Multi-step flows under concurrent access.** When a flow reads state then writes state (check-then-act), test two callers racing through the same flow simultaneously. Use a barrier / sync primitive to ensure they hit the critical section at the same time — `WaitGroup` / `Promise.all` alone doesn't guarantee simultaneity.
- [ ] **"Use once" tokens consumed correctly.** Any token that should be single-use (password reset, verification code, invitation) must be tested with two concurrent consumers. Exactly one must succeed.
- [ ] **Rate-limit enforcement under concurrency.** Count-then-insert rate limits can be bypassed by concurrent requests that all read the same count before any insert. Test with burst requests.
- [ ] **Idempotency under retry/concurrency.** If an operation should be idempotent (accepting an invitation twice, retrying a failed payment), test concurrent execution — the second attempt must not produce a 500 from a constraint violation.
- [ ] **Bootstrap / first-time races.** First-user, first-org, or any "only if none exist" flow tested with concurrent attempts. Exactly one must win.

---

## 6. Boundary & Configuration Validation

Configuration errors, bad boundaries, and missing validation are a surprisingly large portion of production incidents. Test the edges.

- [ ] **Default values are tested.** What does the code do when a config value is absent? Crash? Use a default? Silently use zero? All three are possible; the right behavior needs a test.
- [ ] **Invalid config is rejected at load time.** A system that loads invalid config, then crashes on first use of it, surfaces the error too late. Test that config validation runs at load.
- [ ] **Environment-specific behavior.** If code behaves differently in dev vs. prod (feature flags, degraded modes), test both paths. Don't assume dev-tested code works in prod.
- [ ] **Feature flag flip behavior.** Test both flag-on and flag-off paths. A feature behind a flag that's never tested with the flag off can't be safely rolled back.
- [ ] **Timeout and retry boundaries.** If a caller retries 3 times with 5s timeouts, test what happens on the 4th call and on a request that takes 4.9s. The edges matter.

## 7. Test Infrastructure Hygiene

The test suite itself is code. It decays if not maintained. Messy test infrastructure produces flaky tests, which produce lost confidence, which produce skipped tests (see §2).

- [ ] **No shared mutable state between tests.** Each test should set up its own state and tear it down. Tests that depend on previous tests' state are order-dependent and flaky.
- [ ] **Setup / teardown covers the failure case.** If setup partially succeeds then teardown fails, the next test starts from a corrupted state. Teardown must be robust to partial-setup states.
- [ ] **Test doubles are minimal and honest.** A mock that returns fixed data is testing the mock, not the code. Use real implementations where feasible; mock only external boundaries.
- [ ] **No hardcoded time-of-day or timezone assumptions.** Tests that pass at 09:00 UTC but fail at 23:00 UTC are flaky by design. Use injected clocks for time-sensitive tests.
- [ ] **No network calls in unit tests.** A unit test that hits a real API is an integration test with a misleading name. Either mock the boundary or move it to the integration suite.

## 8. Project-Specific Pitfalls (Hangar Bay)

Disciplines discovered in *this* project's own history. Each is marked **🔥** and keeps its load-bearing `TEST-N` ID (referenced from handoff docs, CLAUDE.md, and session memory). These are richer than one-line checks; read the full entry before relying on it.

- [ ] **🔥 TEST-1 — Service-layer-only tests miss HTTP binding bugs.** Constructing a filter/params model directly in Python (`ContractFilters(region_ids=[1])`) bypasses FastAPI's request binding entirely. A filter can work perfectly at the service layer while being unreachable over HTTP. **Do instead:** every API-facing filter gets at least one HTTP-level test that sends real query params through the test client, plus a schema-level assertion (`app.openapi()`) that the param appears where clients expect it. **Bit us:** the four ID-list filters were GET-body-bound and silently ignored over HTTP; all existing tests passed because they only exercised the service layer. See implementation-pitfalls.md FASTAPI-1.

- [ ] **🔥 TEST-2 — Never weaken assertions to fix flaky tests.** If an assertion races, flakes, or fails nondeterministically, the fix is deterministic synchronization or deterministic fixture data — NOT assertion removal or weakening. If synchronization cannot make the assertion pass reliably, STOP and raise it; do not ship a weaker test. Commit subjects touching assertions state what happened to them ("add", "strengthen", "preserve", or explicitly "weaken" with rationale) — never hide erosion behind "CI stability fix". Prefer mechanism assertions (state observed) over symptom assertions (timing bounds) where feasible.

- [ ] **🔥 TEST-3 — Ordering assertions need deterministic fixtures with tiebreakers.** Tests that assert result order must build fixture data whose sort keys are strictly ordered (distinct prices, distinct names) or must account for the service's documented tiebreaker. Relying on insertion order or identical sort keys produces tests that pass locally and flake elsewhere. See TEST-2 for what NOT to do when that happens.

- [ ] **🔥 TEST-4 — Pagination tests must cross page boundaries.** A pagination bug that short-changes, duplicates, or skips items is invisible to any test that only fetches page 1 of a single-page result set. **Do instead:** fixtures large enough for ≥2 pages; assert union-of-pages equals the full expected set, intersection is empty, each non-final page is exactly `size` items, and `total` matches. **Bit us:** joined-row pagination (implementation-pitfalls.md SQLA-1) survived a full test suite that never crossed a page boundary.

- [ ] **🔥 TEST-5 — Frontend hook/component tests stub the network at the fetch seam.** Stub `fetch` (via `vi.stubGlobal` or openapi-fetch's injectable `fetch` option) with recorded response shapes; assert both the rendered outcome AND the request URL when the contract matters (e.g. repeated array params `region_ids=1&region_ids=2`, gated `search` under 3 chars never sent). Do not mock the hook itself in component tests — that tests the mock. `await` RTL's `findBy*`/`waitFor` rather than sleeping.

- [ ] **🔥 TEST-6 — Vitest's default glob swallows Playwright specs.** Vitest's default include (`**/*.{test,spec}.*`) matches Playwright's `*.spec.ts` files, so Playwright suites fail under `vitest run` with "Playwright Test did not expect test.describe() to be called here" — one failed *file* while all unit tests pass. **Do instead:** keep Playwright in `e2e/` and exclude it in the vitest config (`exclude: [...configDefaults.exclude, 'e2e/**']` in `vite.config.ts`), and keep unit tests on the `*.test.ts(x)` suffix. **Bit us:** the first E2E spec landed as `e2e/default-view.spec.ts` and broke `npm run test` (2026-07-12).

- [ ] **🔥 TEST-7 — Error-state tests must account for the QueryClient's retry policy.** The production QueryClient retries failed queries (retry: 1; `useContract` retries non-404s once), so an error state only renders after ALL attempts fail. A stub that fails only the first call auto-recovers on the retry and the error branch never shows — the test hangs or passes vacuously. **Do instead:** responders/stubs fail as many consecutive calls as the retry policy will issue (list: calls 0 AND 1), then let an explicit user Retry succeed; assert the alert appears before and the data after. **Bit us:** `states.spec.ts` error tests during the 2026-07-12 E2E build-out (caught by the author agent, never shipped red). Relates to §3 Error Path Coverage.

- [ ] **🔥 TEST-8 — Two `role="status"` nodes coexist during list loading.** The loading skeleton (`ContractTable.tsx` `role="status"` named "Loading contracts") and the always-mounted results live region are both `role="status"` while a fetch is in flight, so a `getByRole('status')` assertion polling during load hits a Playwright strict-mode violation (multiple matching nodes). **Do instead:** synchronize on the skeleton unmounting (`waitForDataRendered` / skeleton count 0) before asserting on the results live region; never weaken the assertion to a `.first()`/`.all()` workaround that papers over the ambiguity. **Bit us:** DISC-EXEC-1, Phase 0 of the M2 EVE SSO plan (2026-07-12).

- [ ] **🔥 TEST-9 — Every fixture-lane E2E spec must intercept `GET /me`.** Once the header issues a real `/me` identity request, any fixture-lane spec that does NOT stub `/me` leaks a live request into the mocked lane. **Do instead:** every fixture-lane spec calls `interceptCurrentUser` (401 by default) in every test, even ones that don't otherwise touch auth. **Bit us:** M2 Phase 8 frontend auth-header work (2026-07-12).

- [ ] **🔥 TEST-10 — `ASGITransport` does not run lifespan; wire `app.state` manually in the fixture.** `httpx.ASGITransport` bypasses the app's lifespan startup, so any app-state set up in a `lifespan` handler (`app.state.redis`, `app.state.http_client`) is never populated for tests built on it. **Do instead:** the `auth_client` test fixture sets `app.state.redis` / `app.state.http_client` by hand, and depends on `httpx_mock` structurally so no auth test can reach the network. **Bit us:** M2 Phase 6 auth API route tests (2026-07-12).

- [ ] **🔥 TEST-11 — Writer-side bulk inserts need a test that crosses one chunk boundary.** A bulk insert split into fixed-size chunks (asyncpg caps a statement at 32767 bind params, so the matcher inserts ≤1000 rows/statement) has an off-by-one or last-chunk-dropped bug that is invisible to any test whose match set fits in a single chunk. **Do instead:** arrange a match set strictly larger than one insert chunk (e.g. > `NOTIFICATION_INSERT_CHUNK` rows) and assert every row lands — `created == len(match_set)` and the union of inserted dedup keys equals the expected set. **Bit us:** pre-empted in the M3 watchlist matcher (`services/watchlist_matcher.py`, `NOTIFICATION_INSERT_CHUNK=1000`); pairs with implementation-pitfalls SQLA-2 (the chunked insert is the same statement that carries the partial-index ON CONFLICT). Relates to §4 Bounded growth. **The same rule applies to chunked READS:** a chunked `SELECT ... WHERE id IN (chunk)` loop that only ever sees one chunk in tests passes with a `break` after the first chunk — at corpus scale the de-chunked form blows the same 32767 bind cap and aborts the whole run. Bit us (pre-empted in review): Plan A's skip-select (2026-07-27) had no read-side boundary test until a `break`-after-first-chunk mutation survived the suite; `test_skip_select_reads_across_the_chunk_boundary` now pins it.

- [ ] **🔥 TEST-12 — A characterization test that has not been mutation-verified is not evidence.** A test written by reading code and predicting behavior costs nothing to write and looks identical whether it *constrains* the behavior or merely *agrees* with it. A passing run proves only the latter. **Do instead:** before calling the test done, break the exact behavior the test is named for, confirm the test goes red, then revert — and record the failure output as the evidence. Mutate observability assertions separately (replace the `logger.*` call with `pass`, keeping control flow): a test can go red purely on an escaping exception while its `caplog` assertion is decorative. When two reviewers disagree about whether a test is vacuous, run the mutation instead of arguing — it settles it in seconds. **Revert mechanics matter when the fix is still uncommitted:** restore each mutation from a `cp` snapshot, never `git checkout -- <file>`, which restores from HEAD and silently discards the uncommitted fix along with the mutation — the next mutation then no-ops and its red run reads as "the mutation killed the test" when it is really the original defect failing. Guard each mutation with an `assert <target> in text` so a missing target aborts loudly, and always finish with a restore-and-rerun that must come back GREEN; a red restore run means the baseline was clobbered, not that the fix is wrong. **Bit us repeatedly:** three of the four C901 refactor phases (2026-07-18) produced a vacuous characterization test, two of them written *exactly* as the plan specified — the SQLA-1 tiebreaker test passed with the `contract_id` tiebreaker deleted AND with the two fetch paths merged (one matching item per contract meant the join produced no duplicated rows, and ascending insert order made heap order accidentally match); a structure-ID test asserted a name was NULL for an id the stub map never named anyway; and a `_build_contract_rows` call-site seam passed with an empty name map. Relates to §3 Error Path Coverage and TEST-2 (mutation-verify rather than weaken).


- [ ] **🔥 TEST-14 — `pytest.mark.vcr` on a test that drives our own app replays a cassette and never reaches the app.** vcrpy intercepts *below* `httpx`, ahead of `ASGITransport`, so an API test carrying that marker records a cassette on its first run and thereafter asserts against that recording — not against the application, the database, or any code you just changed. It passes identically whether the behavior it names works or is deleted. **Do instead:** keep the `vcr`/`esi_live` pair on tests of the client-to-ESI interaction only — never on tests of our own database or internal endpoints, which is what `design/fastapi/guides/09-testing-strategies.md` §5 said all along. API tests belong in a module whose `pytestmark` is `asyncio` only (`tests/api/test_contracts.py`, `tests/api/test_contract_filters.py`). Treat an unexpected new file under `tests/api/cassettes/` as the signal that a test is not running what you think. **Now enforced at collection time:** `tests/marker_guards.py` aborts the run when any item pairs the `vcr` marker with an app-client fixture (`client` / `auth_client`), naming every offender; it is wired in via `pytest_collection_modifyitems` in `tests/conftest.py` and covered by `tests/test_marker_guards.py`. Mutation-verification (TEST-12) is still the only thing that catches a *novel* variant of this, and only if the mutation is run against *that* test, since sibling non-VCR tests in the same run will fail correctly and mask it.

  **Bit us:** the M5 expiry filter (2026-07-26) added `test_detail_still_serves_an_expired_contract` to the VCR-marked `tests/api/test_contracts.py`; it passed with the expiry predicate deleted, leaving the branch's headline decision — that the detail endpoint deliberately keeps serving expired contracts — with zero effective coverage. The same module hid eight fixtures with a hardcoded past `date_expired` (TEST-17). Measured 2026-08-01 by stripping the marker and re-running: the pre-fix literals fail 4/5 with `assert 0 == 10`, and with the marker restored those same broken literals pass 5/5 again.

  **The root cause was a misapplied marker, not a recording that went stale.** Every one of the module's five committed cassettes recorded `http://test/contracts/...` — the module's *own* ASGI traffic. Not one of the nine recorded interactions ever touched ESI, so nothing in the module ever needed VCR; the marker had simply been applied to a file of internal-endpoint tests, and vcrpy dutifully recorded the app talking to itself. That also explains the superseded data: the cassettes carried `date_expired: "2025-01-02T00:00:00Z"` from a recording made before the expiry filter existed, so the replayed responses encoded behavior the app no longer has. Fixed 2026-08-01 by dropping the `vcr`/`esi_live` markers, deleting all five cassettes, and mutation-verifying each of the five tests against the real app. **When a cassette exists for a test you did not expect to be recorded, read its `uri:` lines before anything else** — a cassette full of your own base URL means the marker is in the wrong place, and no amount of re-recording will fix it. Relates to TEST-12, TEST-20 (the same module's envelope test was *also* unfailable, for an unrelated reason), and §7 (test doubles must be honest).

- [ ] **🔥 TEST-15 — A zero from an uninstrumented instrument is not a measurement.** Before concluding "there is none of X," prove the instrument can see X at all. **Do instead:** deliberately produce the thing you are looking for, confirm the tool reports it, and only then trust an empty result. **Bit us:** a `PerformanceObserver` with `buffered: true` for `longtask` returned zero entries, which was nearly reported as "no main-thread blocking." Chrome keeps **no buffer for `longtask`**, so buffered retrieval returns nothing retroactively — validated by blocking the main thread for 220 ms and still reading zero, while the identical `buffered: true` flag works correctly for `paint`. The same discipline applies to grep ("no matches" may mean a wrong pattern — a `--include='*.py'` glob silently eaten by zsh returned "no matches found" rather than searching), to API probes ("no results" may mean a wrong parameter name — querying `ships_only` instead of `is_ship_contract` returned the unfiltered corpus and looked like a broken filter), and to any absence-of-evidence claim. Relates to TEST-12: mutation verification is this same rule applied to tests.

- [ ] **🔥 TEST-16 — Measure the population the user actually sees, and carry the sample scope wherever the number is used.** A ratio computed over the whole table can be true and irrelevant. **Do instead:** re-run any product-data measurement with the frontend's default filters applied, state the population beside the number, and treat a single sample as an order of magnitude rather than a constant. **Bit us repeatedly in one session:** "12% of contracts are expired" was true of all 51,365 contracts and meaningless for users, who get a ships-only default of 622 — the corrected figure was ~8.5%, *smaller but sharper*, because 53 dead contracts against a 50-row page means the whole first page of the most natural sort is dead. Separately, a warm page-load latency of 1265 ms was quoted from a single sample that turned out to be the slowest of four, then ~650 ms from four samples that were all contaminated by a long-lived browser tab; the true figure in a clean tab was ~450–500 ms. Each successive correction made the change under evaluation look worse, and the first two numbers had already been written into a merged design. Relates to TEST-12 and §7.

- [ ] **🔥 TEST-18 — A fixture that hand-writes a column ingestion never writes makes a dead feature look tested.** A test fixture constructs rows in Python, so it can populate any column the MODEL declares — including ones no ingestion path ever fills. Every layer then agrees the feature works: the query is correct, the test honestly asserts what it says, and the filter still returns zero rows against every real row in production. This is not the "wrong fixture value" trap — the fixture is internally consistent, and only a comparison against the WRITER exposes it. **Do instead:** before trusting any filter test, open the ingestion mapping and confirm the column being filtered is actually assigned there. Reconcile the fixture's column set against the writer's, never against the model — the model declares what *may* exist, the writer decides what *does*. Where a fixture must keep a column the writer does not populate (to pin query binding, say), state that in the fixture docstring so the next reader cannot mistake presence for coverage. **Bit us three times over in a single fixture** (`tests/conftest.py::setup_contracts`, found 2026-08-01): `is_blueprint_copy=False` (ESI sends that flag only as true-or-absent, so `is_bpc=false` matched zero production rows while `test_filter_by_is_bpc` passed), `raw_quantity=10` (a field carried only by ESI's *authenticated* item routes, so `min_runs`/`max_runs` filtered a permanently-NULL column while `test_filter_by_bpc_runs` passed — since fixed: ingestion writes the public `runs` field, the filter reads it, and the fixture sets `runs=10`), and `start_location_system_id` (at the time never assigned by `_build_contract_rows`, so the `system_ids` filter was inert while two tests asserted it worked — since fixed: ingestion now resolves NPC stations via `/universe/stations/`, and the fixture's values match what it writes). Mutation verification (TEST-12) does NOT catch this — the mutation and the fixture both live in test-land. Relates to implementation-pitfalls ESI-3 and FASTAPI-2.

- [ ] **🔥 TEST-19 — A single-child fixture cannot tell a parent-level predicate from a per-row one.** When a filter classifies a parent by its children ("contracts containing a blueprint copy"), every fixture whose parent has exactly ONE child passes identically whether the query asks about the *contract* or about the *row* — the two readings diverge only when one parent holds children of BOTH kinds. Coverage built from one-item contracts therefore says nothing about the semantics that matter, and the bug it misses is silent: the same parent comes back under a filter AND its negation, with no error and totals that quietly exceed the corpus. **Do instead:** for any parent-classifying filter, include a fixture parent holding both a matching and a non-matching child, assert it appears under exactly one branch, and assert the two branch totals sum to the unfiltered total. Treat "these two branches partition the set" as the property under test — it is NOT implied by either branch being individually correct. **Bit us:** `is_bpc` (2026-08-01) — a contract bundling a BPC with a hull matched both `is_bpc=true` and `is_bpc=false`; every fixture contract had a single item, so the entire suite passed, including the test written that same day for the neighbouring NULL-handling defect. Caught in adversarial review of PR #98, not by the tests. Relates to implementation-pitfalls SQLA-3 and to TEST-18.

- [ ] **🔥 TEST-13 — Playwright `testMatch`/`testIgnore` regexes match the full absolute path, so a checkout directory name can hijack them.** A worktree (or any parent directory) whose name matches a project's pattern — e.g. a worktree slug containing `live-smoke` against `testMatch: /live-smoke/` — makes EVERY file in that checkout a "test file", and collection dies with `test file "X" should not import test file "Y"` errors that reproduce in that checkout only (CI and other clones stay green, which misdirects debugging toward version skew). **Do instead:** anchor the pattern to a path structure a single directory segment cannot fake (`/e2e\/live-smoke/`), and when a Playwright collection error appears in exactly one checkout, diff the checkout PATHS against the config's regexes before anything else. **Bit us:** the CD empty-dataset smoke fix (2026-07-21) was developed in a worktree named `live-smoke-empty`; every spec in the tree became a "test file" until the worktree was renamed and the regexes anchored.

- [ ] **🔥 TEST-17 — A fixture date that is only *currently* in the future is a time bomb with a fuse, not a constant.** A hardcoded literal like `date_expired=datetime(2026, 7, 1) + timedelta(days=30)` is comfortably future-dated the day it is written and silently becomes past-dated later. Nothing changes in the repo on the day it arms: a green suite turns red on a calendar boundary, on a branch whose diff cannot explain it, and the failure lands on whoever pushes next rather than on its author. **Do instead:** anchor any date an expiry/liveness predicate reads to `datetime.now(timezone.utc) + delta` so it moves with the clock, and keep literals only for values the assertion needs to be *stable and distinct* (sort keys, tiebreakers). Both roles usually coexist in one fixture — fixed `date_issued` for deterministic ordering, relative `date_expired` for liveness — and conflating them is the trap. When a test fails with an empty result set and no relevant diff, check the fixture dates against today before anything else. **Bit us:** `test_unmapped_sort_falls_back_to_date_issued` (2026-08-01). The expiry filter added on 2026-07-26 (`contract_service.get_contracts` filters `date_expired > now()`) made that test's fixed 2026-07-31 expiry load-bearing; it passed for five days, then turned `dev` CI red on 2026-08-01 with `assert [] == [940003, 940002, 940001]`, so every PR opened that day inherited a red baseline it did not cause.

  **The quiet failure mode is worse than the loud one.** A time bomb only turns CI red where an assertion happens to read the affected value; everywhere else it just silently changes what the suite exercises, and no one finds out. The 2026-08-01 repo-wide sweep found exactly one loud bomb and a long tail of quiet ones: every `date_expired` in the frontend fixtures had drifted into the past, so the entire E2E and component suite had been rendering its "Time left" column as `Expired` — the `timeRemaining()` / `timeAgo()` formatters read the real `Date.now()` at their production call sites — while the backend's list endpoint had meanwhile begun excluding expired rows, making those fixtures a response the real API can no longer produce. Nothing failed, because **no assertion anywhere read a countdown**. **Do instead:** build fixture dates from the clock (`e2e/fixtures/contracts.ts` `expiryInDays()`, `src/test/dates.ts` `daysFromNow()` / `minutesFromNow()`) and keep at least one assertion that reads the clock-dependent output, so the anchoring is load-bearing rather than decorative — an anchored fixture no test observes is a gap documented, not closed. Assertions on the formatters themselves stay literal-vs-literal by injecting `now` (`format.test.ts`); only *fixtures* go relative. **Gap closed 2026-08-01,** after measuring it rather than estimating: injecting a marker at each helper's entry showed 28 tests across 8 files reaching `timeRemaining`/`timeAgo`, while replacing each body with a sentinel showed only 5 constraining the output — and just one at a production call site, with `timeAgo` at zero despite 8 component tests rendering it 98 times. Ten tests now pin the boundaries that were unpinned, including the exact-expiry instant (`<=`, not `<`), the sub-minute clamp that stops a live contract reading `0m`, and a future `created_at` from server clock skew reading `just now` rather than `-1m ago`. **Relative fixtures need a pad in the future direction only:** a bare `minutesFromNow(20)` floors to `19m` the instant any time elapses, so future offsets carry a half-minute of slack; past offsets need none, since elapsed time only lengthens an already-floored span.

  **A mechanical guard now runs on every PR: `npm run test:future-clock`** (`app/frontend/web/vitest.future-clock.config.ts`, wired as a step of CI's `frontend` job) re-runs the whole vitest suite with `Date` faked 400 days ahead. It bans no pattern and needs no allowlist — it tests the property directly, so a real bomb fails it by construction while the inject-`now`, assert-literal-against-literal formatter tests stay legal. Demonstrated 2026-08-01 by planting a `date_expired` 45 days in the future, indistinguishable from a safe fixture that day: the ordinary lane passed 192/192, the future-clock lane failed 2. **The faked instant MUST stay relative to the real clock** (`Date.now() + 400 days`, pinnable via `HB_FUTURE_CLOCK` to replay a failure) — a fixed instant stops testing the future the moment real time passes it, making the guard against time bombs a time bomb. A rejected alternative was a scanner banning future-dated literals: legitimate pinned dates exist, so it would need an allowlist, and allowlists rot until they mean nothing. **Frontend only, deliberately:** the backend's liveness predicates compare against SQL `func.now()` — the *database's* clock — which a faked Python clock does not move, so the equivalent lane would have to shift Postgres's clock for a suite whose fixtures are already `datetime.now(timezone.utc) ± delta` throughout.

  Relates to TEST-3 (deterministic fixtures — keep sort keys fixed and distinct even while expiry moves), TEST-12 (mutation-verify the anchoring: revert the fixture to a past literal and confirm red), and TEST-14 (the eight sibling fixtures it recorded are anchored, and that module's VCR replay is now gone, so the anchoring is load-bearing rather than decorative).

- [ ] **🔥 TEST-20 — An assertion block guarded by `if <the thing being asserted>:` is a skip that no skip count reports.** `if data["items"]: assert ...` reads as defensive politeness and is the strongest form of vacuity available: when the code under test breaks in the exact way that empties the result, the guard goes false and the assertions the test exists for are silently not run — reported as a pass. Unlike `@pytest.mark.skip` there is no marker, no summary line, and nothing to grep; §2's "skipped tests are not passing tests" applies, but none of §2's instruments can see it. **Do instead:** seed the fixture the test needs and assert unconditionally, so an empty result fails on `IndexError` or a `total` mismatch instead of vanishing. If a result really can be legitimately empty, assert *which* case you are in (`assert data["total"] == 0`) rather than branching around the check. Treat any `if`, `for`-over-possibly-empty, or `or []` wrapped around assertions as a coverage claim to verify, and mutation-verify it by making the collection empty (TEST-12). **Bit us:** `test_get_contracts_live` in `tests/api/test_contracts.py` asserted four contract fields inside `if data["items"]:` while seeding no fixture at all — so the block never executed in any run, ever. Its own committed cassette proved it: the recorded response was `{"total":0,"page":1,"size":50,"items":[]}`, i.e. the branch was already dead at record time. The test had two independent reasons it could not fail — this one and the module's VCR marker (TEST-14) — and removing only the marker would have left it a shape-check over an empty list. Fixed 2026-08-01 by seeding a contract and asserting the fields unconditionally; the mutation "endpoint serves an empty page" now fails it with `IndexError: list index out of range`, and passed it before.

- [ ] **🔥 TEST-21 — A stand-in exception must be of the class the code actually meets.** Simulating a dependency's failure with a hand-rolled `RuntimeError("simulated db failure")` tests the shape of the error path, not its content. When what the test asserts is a property of the *rendered* exception — a redaction claim, a message format, a status mapping — a stand-in from the wrong class carries none of the payload the real class carries, so the assertion holds for a reason unrelated to the code under test and keeps holding after the behavior breaks. The tell is a test whose subject is the exception's content but whose fixture chose the exception for convenience. **Do instead:** raise an instance of the class the production path actually raises, populated with the field that makes the assertion meaningful, and add a guard assertion proving the unfixed rendering would have violated the property (`assert secret in str(injected_error)`) so the test cannot go vacuous if that class's rendering ever changes. Then assert against the whole observed record, not the one key you changed. **Bit us:** F008 Task B10 (2026-08-07) — `test_no_search_log_site_echoes_the_raw_query_text` injected a `RuntimeError`, whose `str()` is parameter-free, and asserted only over the `search_terms` payload. The real failure class is `StatementError`, whose `str()` appends `[parameters: {...}]` from the very statement holding the user's search text as an `ILIKE` bind, and the failure site logged it into `error_message` in the same record. The test passed while the invariant it is named for was false. Relates to implementation-pitfalls SQLA-4 and to TEST-12 (mutation would not have caught this either — the mutation and the stand-in shared the blind spot).

- [ ] **🔥 TEST-22 — Ingestion-mapping tests must include a payload that OMITS each upstream-optional field, or a NOT NULL column over one is never exercised.** TEST-18 reconciles fixtures against the writer; this is the mirror: reconcile the writer against the upstream spec's `required` array. A payload fixture naturally carries every field the author has ever seen on the wire, so a mapping like `"price": c.get("price")` feeding a `nullable=False` column passes every suite — the absence path has literally never executed — and the first spec-conformant payload that omits the field aborts the whole ingestion batch with an `IntegrityError` in production. **Do instead:** for each consumed endpoint, take the fields the spec marks NOT required (the drift monitor's snapshot records this per field), and keep one test that feeds `_build_contract_rows`/the upsert a payload omitting them, asserting the row still persists (via a default or a nullable column). FASTAPI-3's chain rule names the invariant ("enforce at INGESTION"); this is the test that makes it load-bearing. **Found by the 2026-08-08 F008 pre-release bug hunt** (`docs/bug-hunts/2026-08-08-f008-prerelease-holistic.md` Bug 1): `Contract.price` is NOT NULL, ESI marks `[].price` optional on `/v1/contracts/public/{region_id}/`, `_build_contract_rows` supplies no default — its neighbours `collateral` and `for_corporation` both do — and no test omits `price`, so a single price-less contract would fail every aggregation run for as long as it stays listed. Relates to TEST-18 and implementation-pitfalls FASTAPI-3 / ESI-3.

## How to Add a Testing-Pitfall

When a bug reaches production (or staging, or late integration testing) because a test was missing:

1. **Identify the topic section** the missing test belongs in. Universal disciplines go in sections 1-7; a discipline discovered in *this* project's history goes in §8 with a `TEST-N` ID and the 🔥 marker. If none of the existing sections fit, add a new numbered topic section.
2. **Write the check item** as a `- [ ]` checkbox. Lead with a bolded imperative ("**X is tested.**"), then one sentence explaining what the check covers and why. Project-specific entries lead with their `TEST-N` ID so it stays greppable.
3. **Mark with the 🔥 marker** if the bug was found in this project's own history: `**🔥 Found in [context]:** one-line note about the observed failure mode`.
4. **Cross-reference implementation-pitfalls.md** if there's a corresponding implementation entry.
5. **Resist the urge to be clever.** "Tests X under condition Y" is better than a novel testing philosophy. These are pass/fail checklist items, not essays.

The test suite is the enforcement mechanism for this document. If you add a check item and don't write the corresponding test, you've documented a gap, not closed one. Close it.
